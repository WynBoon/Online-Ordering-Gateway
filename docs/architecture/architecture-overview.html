Internal — Architecture Reference

Order Gateway Architecture

A single API in front of multiple till platforms — routing orders from Dine Direct's Order Harmony hub into GAAP Unity and Pilot Live, and translating whatever comes back into one canonical order-status vocabulary.

Owner — this gateway Upstream — Order Harmony (Dine Direct) Downstream — GAAP Unity · Pilot Live Region — South Africa

Order Harmony aggregates channels — Uber Eats, Direct Dine, others — and treats every point-of-sale integration as an interchangeable "partner" behind one spec. GAAP and Pilot are not interchangeable. This document exists because that mismatch has to be designed for, not discovered mid-build.

01System context

We own the gateway. Order Harmony is owned by a different company and calls us as a certified POS partner. GAAP and Pilot relationships and API keys are ours, held per restaurant location we onboard — not Order Harmony's, and not necessarily the merchant's.

02The three contracts, compared

Pulled directly from the Order Harmony partner pack and the published GAAP / Pilot OpenAPI specs. This table is the reason the gateway can't treat POS integrations as a single interface with two implementations — the shape of what each side can do is different, not just field names.

Why this matters GAAP is a batch/financial recording API, not an order-management API — it has no concept of "the kitchen accepted this." Pilot is much closer to what Order Harmony expects, but the feedback channel's exact behaviour (status codes, retries, idempotency) still needs confirming with Pilot before certification.

03Ports & adapters

The core domain — canonical order, canonical menu, the five-state status machine — knows nothing about GAAP, Pilot, or Order Harmony's HTTP shapes. Each adapter implements only the ports its POS actually supports and declares capability flags the application layer reads to decide behaviour, instead of scattering if (posType == Gaap) through the order pipeline.

04Handling the GAAP gap

Because GAAP gives no feedback after injection succeeds, the gateway can't honestly report preparing/ready for GAAP-backed locations — it doesn't know either happened. This is a business call as much as a technical one:

  1. Synthesize a status curve — emit accepted on injection, completed after a configurable delay tuned to prep time. Looks plausible on the tablet UI, but isn't driven by the actual kitchen.
  2. Collapse to two states — emit accepted immediately, completed only once a scheduled poll of GET /sales confirms the invoice is TENDERED and not CANCELED. Less impressive, more honest.

Recommendation: start with option 2, treat option 1 as a UX enhancement once real prep-time data exists per location — and ask GAAP directly whether a real-time kitchen/order channel exists outside this Data-API, since a pure BI/accounting endpoint being the only injection path for live orders would be unusual.

05Where the state lives

Group → Store → ChannelConnection + PosConnection + BillingPlan is the core of the data model — a Store carries the Order Harmony key we issue, a timezone, a lifecycle state (Draft/Active/Paused/Deactivated), and points at either a GAAP nodeId/locationId or a Pilot vendorId/siteId. There's no persisted product-mapping table — the gateway passes product/modifier identifiers straight through as the POS's own native ids, so external_product_id never needs translating.

Idempotency is enforced at every hop with a different key: Idempotency-Key inbound from Order Harmony, a deterministic externalTransactionId (UUIDv4 derived from order_ref) outbound to GAAP, and a stable event_id on every outbound status webhook — retried 1s, 5s, 30s, 2m, 10m, never regressing a terminal status.

06Azure shape

  • Compute, split by workload — Azure App Service (min 1 instance, deployment slots for zero-downtime deploys) for the Order Harmony-facing API; Azure Functions on Flex Consumption for everything reading off Service Bus (webhook retries, GAAP status timers, scheduled menu re-pull). No containers to manage on either side.
  • Static egress IP — VNet Integration + NAT Gateway on both. Order Harmony's certification checklist asks for our source IP ranges to allow-list.
  • Database — Azure SQL or Postgres Flexible Server for stores, connections, mappings, orders, event history.
  • Async plane — Service Bus queue decoupling outbound webhook retry/backoff from the request path; PeekLock + outbox pattern for near-zero message loss across deploys.
  • Secrets — Key Vault for every POS credential and the Order Harmony HMAC signing secret; managed identity, nothing in config.
  • Observability — Application Insights, correlated end to end by order_ref.

07Open questions

Things that need an answer from each party before certification, not assumptions to code around silently.

GAAP

  1. Any real-time order/kitchen channel outside this Data-API?
  2. Production rate/pagination limits beyond the sandbox cap of 5.
  3. How do we source and keep in sync nodeId, employeeId, paymentMethodId for injected sales?
  4. Does one apikey cover a merchant's whole estate, or one per location?

Pilot

  1. The full orderStatus.statusCode integer table.
  2. Exact payload Pilot POSTs to our callbackUrl.
  3. Idempotency behaviour on OnlineOrder/Create replay.
  4. vendorId registration process end to end.

Order Harmony

  1. Sandbox base URL and per-location key issuance flow.
  2. Webhook signing-secret exchange method.
  3. Confirm our declared rate limits before go-live.
